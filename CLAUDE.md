# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A course management system built on Salesforce. The project grows organically — start small, expand incrementally. Each new capability is added in a focused, self-contained change with its own data migration instructions when schema changes are involved.

## Principles

- **Use `sf` CLI to scaffold new files** rather than generating them from scratch. The CLI produces up-to-date, API-version-correct templates. Only hand-write a file when `sf` has no command for it.
- **Incremental growth**: add one feature at a time. Do not introduce abstractions or metadata types that aren't yet needed.
- **Self-contained changes**: every PR or change set must include, in the same commit, any deployment steps and data migration instructions a developer or agent needs to apply it end-to-end.

## Prerequisites

- Salesforce CLI (`sf`) — install via `npm install -g @salesforce/cli` or the official installer
- An authorized Salesforce org: `sf org login web --alias <alias>`

## Common Commands

```bash
# Scaffold new metadata (prefer this over writing files by hand)
sf apex generate class --name MyClass --output-dir force-app/main/default/classes
sf sobject generate field --sobject Course__c          # interactive field creation
sf lightning generate component --name MyCmp --type lwc --output-dir force-app/main/default/lwc

# Deploy to a scratch org or sandbox
sf project deploy start --source-dir force-app

# Run all Apex tests
sf apex run test --test-level RunLocalTests --synchronous

# Run a single test class
sf apex run test --class-names CourseServiceTest --synchronous

# Open the default org in a browser
sf org open
```

## Project Structure Convention

Follow the standard SFDX project layout generated by `sf project generate`. Metadata lives under `force-app/main/default/`. As the project grows, introduce sub-directories by feature (e.g. `force-app/main/default/classes/courses/`) rather than by metadata type alone.

## Data Migrations

Any change that adds, removes, or modifies a custom field or object must include a `migrations/` entry alongside the metadata change. Use the following format:

```
migrations/
  YYYY-MM-DD_<short-description>.md
```

Each migration file must cover:
1. **What changed** — the metadata affected
2. **Deploy steps** — ordered `sf` CLI commands to apply the change
3. **Data backfill** (if needed) — an Apex anonymous script or Data Loader instructions to populate existing records
4. **Rollback** — how to reverse the change if it needs to be undone

## Adding a New Feature

1. Define the data model first (`sf sobject generate field` or create a new object via `sf sobject generate`).
2. Write the Apex business logic (`sf apex generate class`).
3. Write an Apex test class alongside it (`sf apex generate class --name <FeatureName>Test`).
4. Wire up any UI as an LWC (`sf lightning generate component --type lwc`).
5. Add a migration file in `migrations/` if the schema changed.
6. Deploy and verify: `sf project deploy start && sf apex run test --test-level RunLocalTests --synchronous`.
